# Direct QUIC through Hattori eth0

Date: 2026-09-22, Asia/Tokyo.

## Result

The repaired QUIC traversal established an authenticated direct connection between yutoms and Hattori through `eth0`.
The connection passed all path checks during eight TCP payload trials and two UDP payload trials.
No gateway access or static port mapping was required.

The TCP tests used QUIC as the underlay. They did not use H2 or WSS.
The current Tailscale probe used a peer relay. It did not establish a direct connection.
These results therefore do not establish a matched performance comparison with Tailscale.

## Cause and repair

yutoms has destination-dependent UDP mappings. Its STUN endpoint did not identify the mapping used toward Hattori.
Hattori also filtered unsolicited packets from destination ports that it had not contacted.
Probing only the STUN candidates could not establish this pair.

The repair uses 128 sockets on the variable-mapping side.
The stable-mapping side searches at most 4,096 shuffled ports on the authenticated peer's public IPv4 address.
Probes retain their interface binding and use standard STUN messages.
The search sends at most 200 probes per second. Socket-pool probes send at most 125 per second.
Only one hard-NAT attempt can run per instance. The attempt has a 28-second traversal timeout.

The initiator nominates one successful endpoint pair through a separate STUN transaction.
The responder confirms that pair. This prevents crossed probes from selecting different mappings.
The selected socket passes directly to QUIC. All unused sockets close.
QUIC retains admission checks, TLS exporter binding, Noise authentication, and expected-peer validation.

Each probe socket requests 16 KiB receive and send buffers.
The 128-socket pool therefore requests 4 MiB in total, before operating-system accounting.
Linux normally doubles reported buffer sizes. QUIC restores its normal buffers only on the selected socket.
This is a queue limit, not a claim about resident allocation.

For uniformly distributed ports, 128 mappings and 4,096 candidate ports give an approximate overlap probability of 99.97%.
Real NAT allocation and filtering can violate this model. The implementation still requires bidirectional confirmation.
The new search covers one variable-mapping peer and one stable-mapping peer.
Two variable-mapping peers retain the ordinary candidate procedure.
`disable_udp_hole_punching` disables this coordinator. `disable_sym_hole_punching` disables the new search.

## Verified path

| Host | Interface | Local QUIC endpoint | Peer endpoint |
| --- | --- | --- | --- |
| Hattori | eth0 | 192.168.64.23:55906 | 133.1.22.2:44111 |
| yutoms | en1 | 172.25.23.12:64208 | 217.178.105.142:55906 |

The coordinator selected the path after Hattori sent 418 port-search probes.
Both peers reported `p2p`, `quic`, and `NetworkSecretConfirmed`.
Every trial checked peer status and detailed endpoints before, during, and after transfer.
Each trial retained the same connection ID throughout its three checks.
Every trial captured 20 early large packets on Hattori's selected UDP port through `eth0`.
The captures were not continuous recordings of the complete transfers.
The selected-port captures contained no `pppoe-bbd` or `tailscale0` packets.
Management SSH used Tailscale. The transfer payload used the direct QUIC connection.

The relay at S6916 carried discovery and rendezvous RPC traffic.
Relay counters increased by only 604–3,413 bytes per endpoint and trial.
It did not carry the measured direct payload.
Hattori's eth0 MTU was 1,500. The overlay MTU was 1,280.
QUIC path samples reported a 1,420-byte UDP payload MTU throughout the TCP trials.

## Throughput

Upload means yutoms to Hattori. Download means Hattori to yutoms.
Each TCP combination ran twice for 20 seconds. The table reports receiver goodput.

| TCP streams over QUIC | Upload median, Mbit/s | Upload range | Download median, Mbit/s | Download range |
| --- | ---: | ---: | ---: | ---: |
| 1 | 182.52 | 177.44–187.60 | 260.01 | 259.07–260.95 |
| 4 | 238.89 | 236.17–241.60 | 250.10 | 248.79–251.41 |

yutoms used the LowTier userspace TCP forwarder. Hattori used a TUN interface.
The receiver/sender TCP byte-counter ratios ranged from 91.51% to 98.81%.
These ratios are not packet-loss measurements. Sender counters include data still queued when a timed transfer ends.
The reported goodput uses only receiver bytes.

The UDP checks used 1,000-byte payloads at 10 Mbit/s for 15 seconds, once per direction.

| Direction | Receiver goodput, Mbit/s | iperf sequence loss | Jitter, ms |
| --- | ---: | ---: | ---: |
| Upload | 9.994 | 0 / 18,750 | 0.174 |
| Download | 10.000 | 1 / 18,762, or 0.00533% | 0.374 |

The download UDP received/sent byte ratio was 99.9467%, which differs from the sequence-loss ratio.
The raw sender and receiver counters remain in the saved results. The boundary difference was not resolved.
The upload UDP byte ratio was 100%.
These low-rate checks establish delivery at the tested load. They do not establish maximum UDP throughput.

## Latency, loss, CPU, and memory

The initial peer latency was about 8 ms.
Peer latency samples across the matrix ranged from 7.99 to 14.65 ms.
These are peer heartbeat measurements, not application latency percentiles.

QUIC sender packet-loss estimates during TCP uploads ranged from 0.035% to 0.439%.
QUIC sender packet-loss estimates during TCP downloads ranged from 0.0084% to 0.0262%.
The estimates use adjacent cumulative path samples around each transfer, with observation windows of approximately 21–26 seconds.
Linux reported 46 and 100 inner TCP retransmissions for the single-stream downloads.
It reported 97 and 140 for the four-stream downloads.
The macOS userspace-forwarded upload path did not expose comparable inner TCP retransmission counts.

The following values are median process CPU seconds per receiver-delivered Gbit.
CPU samples ran once per second for about 24 seconds around each 20-second transfer.
They include daemon baseline work and RPC activity. No idle subtraction was applied.

| Streams | Direction | yutoms CPU s/Gbit | Hattori CPU s/Gbit |
| --- | --- | ---: | ---: |
| 1 | Upload | 3.16 | 3.38 |
| 1 | Download | 3.00 | 2.31 |
| 4 | Upload | 2.72 | 3.14 |
| 4 | Download | 3.24 | 2.59 |

Observed process RSS across the TCP trials ranged from 29.38 to 85.81 MiB on yutoms.
It ranged from 26.69 to 44.42 MiB on Hattori.
These ranges include retained memory from earlier trials in the same process.
The CPU figures exclude iperf and kernel work charged outside the LowTier process.
Hattori's aggregate host CPU counters were also saved, but they do not isolate this VPN's kernel cost.
No CPU-efficiency claim against WireGuard or Tailscale follows from these measurements.

## Tailscale, H2, and WSS

The current Tailscale probe returned one DERP response and four peer-relay responses through S6916.
The peer-relay latency was 25–27 ms. The command ended with `direct connection not established`.
This establishes the observed probe result, not a general limit on Tailscale traversal.

H2 and WSS use TCP underlays. This repair establishes UDP paths for QUIC.
No direct eth0 H2 or WSS measurement was obtained in this run.
The older H2, WSS, and Tailscale measurements used Hattori's PPPoE interface.
Those measurements are not matched controls for the eth0 results above.
