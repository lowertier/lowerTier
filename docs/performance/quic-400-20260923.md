# LowTier Q8: QUIC WAN throughput, correctness and resource acceptance

Date: 2026-09-23. Source commits: `ba1bdd96cb00102cb4f1fcffebbc911fd066e6ee` and `7aeadc7a493f30812d24d89dd5e3057bfa385a1f`.

## Outcome and scope

All ten final sequential-direction acceptance runs exceeded 400 Mbit/s receiver goodput on the public osku–UTMOWRT path. The three short single-flow repetitions produced medians of 621.715 Mbit/s upload and 530.197 Mbit/s download. The 120-second runs delivered 461.011 and 523.700 Mbit/s respectively. These are transfer averages; a continuous 400 Mbit/s floor has not been established.

The separate simultaneous full-duplex extension did not achieve 400 Mbit/s in each direction. Its two 30-second runs delivered 225.145/311.642 and 101.114/517.175 Mbit/s upload/download. Sequential and simultaneous results are kept separate throughout this report.

Q8 core and compatible CLI were installed on both resident test instances. The default transport is QUIC and MTU flag is 1300, yielding the tested 1280-byte inner IP MTU on osku. Prior C4 binaries and private configuration backups remain available. The active baseline points to Q8.

## Method

Endpoints: osku/macOS arm64 and UTMOWRT/Linux aarch64-musl. The relay was used for discovery/rendezvous; payload acceptance required a public authenticated one-hop QUIC path. Each endpoint had one stable direct connection, correct authentication, matching connection IDs before/during/after transfer, and counters covering the delivered payload. Tailscale addresses were excluded from the payload path. Encryption, TLS exporter binding, PMTUD and the wire format remain enabled and unchanged.

Each test omitted three warmup seconds. Short single-flow tests used three 15-second repetitions per direction and varied the connection initiator. The long check used one 120-second transfer per direction. Four-flow checks used one 15-second transfer per direction. Compiler-contaminated results were excluded. There were no environment overrides for the selected congestion algorithm, precise-timer behavior or burst cap.

CPU and memory were sampled every 250 ms. CPU 100% denotes one logical core. Long-run CPU averages use the entire steady elapsed window from 4 through duration+2 seconds, rather than an initial short slice. CPU/Gbit is average measured process CPU cores divided by receiver Gbit/s. User/system CPU includes work charged to the core process and excludes iperf and unattributed kernel/other-process work. RSS includes shared pages; macOS physical footprint is separate and UTM PSS is unavailable.

## Why the old path was slow

The ideal window-limited delivery rate is 8W/RTT. A 400 Mbit/s path at 13 ms RTT needs approximately 650,000 payload bytes in flight before accounting for headers and scheduling. The recovered CUBIC diagnosis showed a 544,536-byte window and 12,792 microsecond RTT, corresponding to an ideal window ceiling of about 341 Mbit/s. The endpoint NIC rates alone cannot determine the usable end-to-end Internet rate.

Q7 replaced the aggregate CUBIC controller with delivery-rate/minimum-RTT-based BBR. The initial flight stays at 12,000 bytes and the pacing burst cap stays at 64 packets. CUBIC remains an explicit diagnostic choice. A 128-packet burst experiment performed worse, so larger bursts were rejected. The single-run controller/timer ablations are archived and are diagnostic evidence, rather than a statistically isolated estimate of each change.

On macOS, coalesced timer deadlines impeded fine-grained pacing. A requested 250-microsecond timer measured approximately 2.3 ms with ordinary coalescing and 0.30 ms with the critical timer flag. The new runtime reuses a kqueue one-shot timer through Tokio AsyncFd, uses nanosecond units, and requests minimal coalescing only for deadlines below 10 ms. It uses neither a spin loop nor a dedicated worker thread, and falls back to Tokio on setup failure. ACK-triggered work can also release pacing; timer latency alone is not a universal throughput formula.

## New long-run bug reproduced and fixed

Fresh Q7 short runs passed, including upload 548.7–720.6 Mbit/s. A new 60-second upload then fell to 116.067 Mbit/s overall. It began near 600 Mbit/s and collapsed around the RTT-probe transition, with little additional loss during the sustained low-rate state. That failure was retained and blocked Q7 promotion.

The vendored BBR implementation marked transmissions inside ProbeRTT as application-limited, then lost that flight boundary at probe exit. The intentionally drained, small refill flight could replace an aged ten-round maximum-bandwidth estimate. A deterministic regression reproduced an estimate falling from 100,000,000 to 1,200,000 bytes/s.

The correction refreshes the application-limited marker on every ProbeRTT ACK, including the ACK that exits the mode. The first refill therefore retains its limited-flight provenance. The marker still expires, and the same regression verifies that genuine sustained lower delivery can subsequently lower the bandwidth estimate. The runtime change adds no allocation or thread, and leaves probe duration, finite congestion windows, pacing, packet format and queue budgets unchanged. This flight-marking behavior is consistent with the Google QUICHE BBR reference [3].

## Why congestion feedback stays enabled

QUIC DATAGRAM supplies unreliable encrypted delivery without automatic retransmission of the inner IP payload. This separates outer datagram delivery from the inner transport’s reliability loop. RFC 9221 section 5.4 still requires DATAGRAM transmissions to obey the QUIC connection congestion controller [1]. Unlimited injection would neither identify path capacity nor guarantee receiver goodput. The selected design keeps one aggregate model-based pacing controller, leaves individual flows to their inner transport, and avoids adding another application-rate limiter or queue layer.

## Verification and failed-attempt handling

Final functional validation: 295 Quinn protocol tests, 47 LowTier QUIC tests and 25 hole-punch tests, all passing (367 Rust tests total), plus one explicitly executed real Caddy shared-port integration. Both macOS arm64 and Linux aarch64-musl release builds succeeded. Relevant source hashes and deployed/frozen core hashes were checked.

The first attempt to run the new regression failed during ring C compilation because the host searched an unreadable `/usr/local/include/stddef.h`. It was recorded as a build failure. Using the established explicit Clang/SDK include roots allowed the actual assertion failure to run; that failure then passed after the fix.

The first Q8 120-second traffic run delivered 565.470 Mbit/s but its ping observer timed out. It was excluded from acceptance and retained. Only the ping observation timeout was extended; iperf duration, rate and delivery assertions stayed unchanged. A complete repeat supplied the accepted long-run results above.
