# Native H2 proxy measurements

The native H2 proxy is implemented and deployed to the reachable test fleet.
The product default and retained fleet setting are `off`.
The automatic policy passed admission and live configuration checks.
The measurements do not justify automatic performance promotion.

Tests ran on November 17, 2026, in Japan Standard Time.
The raw evidence directory uses its November 16 UTC start date.
Application source is `58f5da69` with the receive-credit repairs in `67ada09f`.
A later documentation commit does not identify the application binary source.

## Scope and policy

The public option is `transport.h2.tcp_proxy = "off" | "on" | "auto"`.
Mode changes apply to new flows.
The native path serves eligible TCP proxy flows to a userspace peer's own IPv4 address.
Ordinary kernel TUN forwarding retains the packet path.
Protected management destinations retain packet handling.
H2 request initiation requires the client side of the carrier.

The automatic policy checks destination scope, authenticated capabilities, local capacity, and native-open health.
A failed open starts a two-second cooldown, which can increase to thirty seconds.
One real flow probes recovery.
The policy sends no background synthetic probes.
An ambiguous open or timeout fails the current flow.
It never replays application data.
A refusal before admission can select packets.
The policy does not estimate transfer speed or loaded latency.

The implementation adds no smux framing or carrier pool.
QUIC retains its existing H3 streams and datagrams.
Obsolete feature names, the old proxy module path, and the diagnostic switch were removed.
No compatibility aliases were added.

## Measurement contract

- Pair: jpaws to LA over a public IPv4 H2 carrier.
- Both isolated nodes use userspace mode.
- Configured overlay MTU: 1300.
- TCP MSS reported by the outer connection: 1448.
- jpaws uses Cubic congestion control. LA uses BBR congestion control.
- Each trial delivers 64 MiB across one or four flows.
- GET moves payload from LA to jpaws.
- PUT moves payload from jpaws to LA.
- Each cell has three repeats.
- Every downloaded byte is checked.
- The upload receiver checks every byte and acknowledges the delivered count.
- Both directions exercise TCP half-close.
- Bulk connections are established before timing.
- Each trial has eleven unloaded echo RTT samples and concurrent loaded echo samples.
- CPU includes user and system time from both LowTier fixture processes.
- CPU excludes the generator, service, SSH, and softirq work outside those processes.
- The server CPU interval includes control gaps and unloaded echo work.
- RSS is sampled every 100 ms and excludes kernel memory.

CPU is reported as seconds per delivered decimal Gbit.
Throughput uses decimal Mb/s.
Cohorts ran sequentially and were not randomized.
The old resident executable forms a separate reference cohort.
The primary comparison uses `off`, `on`, and `auto` in the same candidate executable.
The resident fleet processes stayed active during the isolated speed tests.

## Local TCP memory investigation

The sender socket buffer fell from 2,479,040 bytes to approximately 150–190 KiB during slow trials.
Its congestion window and advertised receive window still allowed more flight.
One slow primary trial had no increase in the recorded outer retransmission counter.
A separate three-run diagnostic reproduced the slowdown.

The host reported 411 MiB of RAM.
Its TCP soft memory threshold was 3630 pages, or approximately 14.18 MiB with 4 KiB pages.
Synchronized socket records showed allocated TCP memory above that threshold.
Four local SOCKS receiver queues each held approximately 2 MiB.
The four generator send queues added approximately 1.6 MiB each.
Carrier send capacity recovered when these queues drained.

The cached upstream Linux source refuses send-buffer growth at the soft TCP memory threshold.
This supports the explanation for failed capacity recovery.
The running kernel is the vendor build `5.14.0-687.59.1.el9_8.x86_64`.
The exact vendor path that first reduced the buffer remains unresolved.
A zero `TCPMemoryPressures` counter does not exclude the separate soft-threshold check.

A matched control bounded only the generator send queues.
Each generator requested a 32 KiB send buffer.
Linux reported 64 KiB for each socket.
The bound corresponds to two existing 32 KiB copy chunks.
Transport limits, receive windows, process limits, and system limits stayed unchanged.

RSS ranges include all sampled values in the original candidate cells.
Sampling can miss shorter peaks.
The traffic measure uses unique TCP payload received in the measurement interval.
It includes TLS, H2 framing, and control traffic.
It excludes outer TCP/IP headers, outer acknowledgments, and duplicate retransmissions.
Most bulk-flow setup occurs before that interval.
Absent `ss` counter fields remain unknown in the machine-readable summary.

For a full inner IPv4 packet, the packet path adds IPv4, TCP, and 20 bytes of LowTier framing.
A 1280-byte MTU with a 20-byte TCP header gives approximately 4.84% data overhead.
TCP options, partial packets, and inner acknowledgments add traffic.
A full 32 KiB native DATA frame adds approximately 0.0275% H2 framing.
This model excludes TLS, control frames, and outer transport headers.
The measured traffic reduction alone does not explain the full throughput difference.
The native path also removes inner TCP packet processing and its recovery loop.

Each native flow reserves a 2 MiB receive window and 64 KiB of copy storage.
The connection window preserves the original 4 MiB packet allowance.
Advertised receive credit remains charged for the carrier's lifetime.
This retained reservation can reduce capacity available to later flows.
It does not account for all kernel TCP queue memory.
The existing process governor and all resource limits remain unchanged.
