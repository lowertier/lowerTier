# s6916 and UTM OpenWrt comparison

Measured on 2026-09-20 UTC and JST.

`s6916` provides substantially more CPU time than JP AWS.
With iperf 3.17.1 on both endpoints, LowTier four-stream medians were within 1.7% of Tailscale.
The earlier four-stream upload deficit was strongly affected by the installed iperf receiver.
The measurements do not establish 10 Gbit/s capacity or general performance equivalence.

## Correctness fix

The first candidate could connect through QUIC but could not receive overlay IP packets on `s6916`.
LowTier cached the TAP MAC address during startup.
Systemd subsequently applied `MACAddressPolicy=persistent` and changed that address.
LowTier then reconstructed Ethernet headers with the stale destination MAC.
An AF_PACKET capture classified those frames as `PACKET_OTHERHOST` despite valid IP and ICMP checksums.

Changing only the temporary TAP address back to the cached value restored all three ping replies.
The patch now subscribes to Linux link events before taking the initial MAC snapshot.
It refreshes the shared MAC after link changes, lost events, or monitor recovery.
The TAP sink loads one atomic MAC snapshot per packet batch.
The instance owns the monitor task and socket. Instance shutdown releases both resources.

The change adds one netlink socket and one waiting task per Linux TAP interface.
Packet processing remains O(P + B), where P is packet count and B is total packet bytes.
The added packet-path work is one atomic load per batch, with no packet-path system call or allocation.
Queued packets can briefly retain the old address during a concurrent MAC change.
The patch does not provide an atomic transition with the kernel interface update.

Nine virtual-NIC tests and two Linux netlink parser tests passed.
Both Linux release targets built successfully.
The patched candidate returned all three live ping replies during a deliberate MAC change.
All three replies also arrived after restoration of the persistent address.

This is a startup and runtime correctness fix. It does not explain the measured upload variability.
The original-source baseline also contained a slow upload after the manual MAC workaround.
No causal throughput improvement is claimed for the MAC change.

## Conditions and resource evidence

`s6916` exposes two Xeon Gold 6148 vCPUs and approximately 978 MiB RAM under KVM.
UTM OpenWrt exposes six aarch64 CPUs and approximately 8 GiB RAM.
During the initial candidate series, `s6916` steal ranged from 0.20% to 4.74%.
Before the workload reduction, JP AWS showed 92–96% steal in fresh one-second samples.
The likely Lightsail burst-capacity constraint is described in the [JP AWS report](jpaws-utmowrt-20260920.md).
The later [JP AWS retest](jpaws-retest-20260920.md) records idle recovery and renewed steal under load.

Before testing, `s6916` had approximately 67–70 MiB available memory and no free swap.
Available memory varied later. Existing production processes remained active.
Major page faults occurred in several processes during the four-stream series.
These observations do not establish memory pressure as the sole cause of the upload deficit.

CPU and memory sampling used `/proc` at five-second intervals over approximately 35 seconds per transfer.
Host CPU includes kernel work, iperf, both overlay services, monitoring, and other processes.
The following values are medians of CPU seconds divided by receiver-delivered Gbit for the one-stream series.

| Host | Direction | Tailscale process | LowTier process | Host CPU with Tailscale | Host CPU with LowTier |
|---|---|---:|---:|---:|---:|
| s6916 | Upload | 3.233 | 3.375 | 3.454 | 3.674 |
| s6916 | Download | 1.543 | 1.853 | 1.476 | 1.763 |
| UTM OpenWrt | Upload | 2.154 | 1.855 | 1.956 | 2.078 |
| UTM OpenWrt | Download | 1.860 | 1.540 | 1.870 | 1.984 |

Process CPU exceeds host active CPU in some records on both hosts.
The saved parser flags these discrepancies. These counters do not support a precise CPU-efficiency comparison.
CPU windows include setup and idle time around each transfer.

During the initial one-stream series, candidate RSS ranged from 15736–28724 KiB on `s6916` and 30312–51124 KiB on UTM.
Tailscale RSS ranged from 288284–436748 KiB and 126872–157160 KiB, respectively.
The candidate had no sampled process swap. `s6916` Tailscale swap ranged from 105352–106912 KiB.
These are sampled process values, not peak allocation or total kernel memory.
Process ages and workloads differ, so these figures do not establish a causal memory improvement.

## Receiver diagnostic

Equal 1 MiB socket buffers did not remove the four-stream upload deficit.
LowTier delivered 131.069 and 170.072 Mbit/s. Tailscale delivered 410.822 and 255.890 Mbit/s.
All four advertised receive windows reached 4768 bytes in several intervals.
Disabling LowTier offload only on `s6916` produced 222.025 and 262.329 Mbit/s.
Matched Tailscale runs produced 412.842 and 363.805 Mbit/s.
Neither experiment established memory pressure or GRO alone as the cause.
The default offload setting was restored.

The receiver observer then sampled the temporary iperf process during a four-stream upload.
The process repeatedly waited in `select` with only descriptor 29 in its read set.
Descriptors 25, 27, and 31 each retained approximately 7–9 MB in their TCP receive queues.
The socket descriptors were nonblocking, and the iperf server had one thread.

The installed package was `iperf3 3.9-1+deb11u3`.
Disassembly of its actual `Nread` function showed a separate `select` call before reading and after partial reads.
This serializes progress across streams in the single-thread server.
Upstream 3.9 source does not contain those waits, so its version string alone did not describe the installed behavior.
The observed serialization is a measurement constraint. It does not prove every slow upload has the same cause.

The temporary replacement uses unmodified official `esnet/iperf` tag `3.17.1` and one worker thread per stream.
It was built locally with Zig for static x86_64 Linux and without OpenSSL.
Only the two task-owned test servers were replaced. The Debian system package remains unchanged.
The executable SHA-256 is `053a0bd845eb80aaffda2d2b51b8b79a9d180259097b15f5312ceca7f48ceadd`.
The downloaded source archive SHA-256 is `105b4fe7fbce31c9b94a3fec10c46e3b4b298adc076e1e3af52b990e1faf2db9`.
See [upstream source](https://github.com/esnet/iperf/tree/3.17.1).

One diagnostic connection timed out after a tunnel restart.
The peer logs showed authentication and route recovery errors during that interval.
The failed run remains in the evidence. All three health pings returned before the loaded observation was repeated.

## Reproduction

The candidate uses commit `1547eb18f340a7067ef24b85daf9b40a321abbad` plus the TAP MAC fix.
The separate launcher change corrects an invalid test cipher fixture.

| aarch64-unknown-linux-musl | `6dd205e7edd55e54a793a481455942a8c01b5eeda53d49732e1a7b4fb073744a` |

`s6916` ran Linux 5.10.0-35-cloud-amd64 and Tailscale 1.102.2.
Its installed iperf 3.9 package served the initial and diagnostic trials.
UTM OpenWrt ran Linux 6.6.110, iperf 3.17.1, and Tailscale 1.94.1.
The matched TCP and UDP series used the temporary iperf 3.17.1 server on `s6916`.
Tailscale endpoint versions differ. Both tunnel paths used the same endpoints and iperf versions within each series.

Candidate instances used isolated interface `lt-speed`, QUIC IPv6 port 14292, and two runtime worker threads.
Secure mode and private mode remained enabled with separate temporary credentials.
LowTier addresses were `10.127.126.50` and `10.127.126.100`.
Tailscale addresses were `100.87.183.91` and `100.109.224.48`.
The configured LowTier MTU was 1280. Its effective interface MTU was 1260; Tailscale used 1280.
Both paths used TCP MSS 1200.

Temporary firewall rules prevented Tailscale traffic from nesting through the test overlay and forced this peer pair onto public IPv6.
TCP tests ran sequentially. Path order alternated between trials.
Path snapshots before and after each trial cannot exclude a change during a trial.

Download adds `-R`. Both server sockets bind only their corresponding test addresses.
Production binaries and configurations were not replaced.
All temporary candidates, iperf servers, firewall tables, staged files, and private test configurations were removed after testing.
Production process checks and UTM executable/configuration hash checks passed after cleanup.
Live Caddy routing and unauthorized-probe integration checks were not repeated for this TAP-only change.
